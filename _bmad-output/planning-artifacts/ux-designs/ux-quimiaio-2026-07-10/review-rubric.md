# Spine Pair Review — Quimia IO

## Overall verdict

The spine pair is a strong contract in shape, discipline, and traceability: canonical DESIGN.md section order, clean token resolution almost everywhere, accurate FR/NFR citations back to the PRD, and all four core product flows (intake, capture, delivery/debt-gate, portal) are named, stepped, and climaxed. It falls short on two load-bearing structural gaps that a downstream consumer would actually trip over: five heavily-specified EXPERIENCE.md components have **no** DESIGN.md visual spec at all, and EXPERIENCE.md points to a `DESIGN.md` "critical-alert" component that does not exist anywhere in the file. Conventional UI states (empty, cold-load, offline, generic error) are also essentially unaddressed across all fifteen IA surfaces despite an explicit PWA/offline claim in Foundation. Close these before handing off to architecture/story-dev.

## 1. Flow coverage — adequate

All four Key Flows (Reception intake, Chemist capture, Delivery/debt-gate, Patient portal) are present in `EXPERIENCE.md`, each with a named protagonist, numbered steps, a marked **Climax**, and a failure path. Cross-checked against the four core requirements named in the brief — reception/order intake, results capture with evidence gallery, results delivery/debt-gate, patient portal access — all four are covered, one flow apiece. This exceeds both example files' Key-Flows count (2 flows each), appropriate given Quimia IO's larger domain surface.

### Findings
- **medium** Flow 4's failure path only covers a wrong date-of-birth entry; it never addresses an expired or already-used token, even though the cited requirement (PRD FR-44) explicitly specifies a *configurable* token policy — "single-use or time-expiring (24h / 7 days)" — with materially different failure UX per model (`EXPERIENCE.md` lines 167–176, esp. 175; PRD `prd.md` line 171). *Fix:* add a second failure branch to Flow 4 (or a State Patterns row) covering expired/consumed-token access, and state which policy (single-use vs. time-expiring) Phase 1 ships with.
- **low** No Key Flow (or explicit state-pattern walkthrough) covers the invalidate → mandatory-reason → recapture cycle end-to-end, even though it's called a "hard requirement" for the lab's ISO 15189 pursuit (`EXPERIENCE.md` lines 88, 92). It's described correctly as a rule, just never dramatized as a flow the way the other four are. *Fix:* optional — a 5th flow or a callout is enough; not required at spine granularity, but worth strengthening before story-dev needs to invent the screen sequence unassisted.

## 2. Token completeness — strong

Extracted every frontmatter token (18 colors, 8 typography roles, 5 rounded scale steps, 12 spacing entries, 13 components) and every `{path.to.token}` reference in the prose and in the `components` block. All resolve — no broken token paths, no color missing a hex value. The two contrast ratios the brief asked to verify are in fact stated with numbers: gray-on-bg ≈4.63:1 and `ok-text`-on-white ≈5.34:1 (`DESIGN.md` line 227), both correctly scoped in `EXPERIENCE.md`'s Accessibility Floor to just those two pairs (`EXPERIENCE.md` line 109).

### Findings
- **medium** `{colors.accent-text}`, `{colors.warn-text}`, and `{colors.error-text}` are all used to carry copy on light surfaces (status-pill "Validado" label, KPI attention delta, kanban-card-aging timestamp, critical-alert headlines — `DESIGN.md` lines 156, 162, 208, 210) but none of them has a stated numeric contrast ratio the way `gray` and `ok-text` do. The Do's and Don'ts table asserts these `-text` variants are the safe way to carry semantic color as copy (`DESIGN.md` line 221) without showing the math that makes that true. *Fix:* extend the "Accessibility contrast — resolved" note (`DESIGN.md` line 227) to state ratios for `accent-text`, `warn-text`, and `error-text` against their actual backgrounds, or explicitly flag them as not-yet-verified.

## 3. Component coverage — thin

Extracted every component name from `DESIGN.md.Components` (11 entries) and `EXPERIENCE.md.Component Patterns` (8 rows), then cross-checked both directions.

### Findings
- **critical** Five components with real, substantial `EXPERIENCE.md.Component Patterns` rows have **zero** corresponding entry in `DESIGN.md.Components` — no color, radius, shadow, or layout spec anywhere: **Evidence gallery**, **Constrained document editor**, **Study reorder**, **Correction history popover**, **Signature pad** (`EXPERIENCE.md` lines 63–67; absent from `DESIGN.md` lines 202–215). These aren't peripheral — the evidence gallery in particular is the component the reconciliation docs flag as the one the client emphasized most ("TE LO ENCARGO MUCHO"), and it anchors Flow 2. A downstream builder has a full behavioral spec and no visual one. *Fix:* add a `DESIGN.md.Components` row for each — even a short one (surface, radius, border treatment, crop-tool chrome, popover styling, signature-pad canvas bounds) closes the gap.
- **critical** `EXPERIENCE.md` explicitly points to a `DESIGN.md.Components` entry named "the dashboard `critical-alert` pattern" for the critical-value acknowledgment visual treatment (`EXPERIENCE.md` line 96) — but no such component exists anywhere in `DESIGN.md` (checked frontmatter `components` block lines 80–140 and prose Components section lines 202–215; only `button-critical`, a button, exists, which resolves the *action* not the *alert card itself*). This is a named reference that does not resolve. *Fix:* add a `critical-alert` component to `DESIGN.md` (or rename the `EXPERIENCE.md` pointer to whatever the intended real component is).
- **low** Conversely, several `DESIGN.md.Components` entries (sidebar-nav-item, primary/critical button, pill input, KPI card, kanban column, status pill, data-table row states) have no row in `EXPERIENCE.md.Component Patterns`. Most of these are low-complexity/generic enough that their behavior is adequately covered elsewhere (Accessibility Floor's focus-ring rule, State Patterns' Caja/debt/critical sections) — this is a lesser miss than the reverse direction above, but status-pill in particular has real behavioral nuance (cancelado is muted not red, adeudo stacks alongside the state pill rather than replacing it — `DESIGN.md` lines 211) that lives only in `DESIGN.md` prose, not in the `EXPERIENCE.md` table where a behavior-spec reader would look first. *Fix:* optional — a one-line status-pill row in Component Patterns would make this discoverable from the behavioral side.

## 4. State coverage — thin

Walked all 15 IA surfaces (`EXPERIENCE.md` lines 24–41) against empty / cold-load / focus / error / offline / permission-denied.

### Findings
- **high** No surface — including Recepción/Órdenes and Captura de Resultados, the two busiest, all-day work surfaces — has a defined offline state, despite Foundation's explicit claim "Mobile-first PWA (NFR-6): every screen must remain usable on a phone" (`EXPERIENCE.md` line 16) and NFR-6's PWA framing in the PRD. Both example reference files (`experience-example-mobile.md`, `experience-example-shadcn.md`) treat offline as a first-class State Patterns row; Quimia IO's State Patterns section (lines 72–98) covers only business/domain state machines (Kanban pipeline, debt-gate, Caja, critical-value) and never once addresses what happens to an in-progress capture or intake form when connectivity drops. *Fix:* add an explicit offline row — even "out of scope for Phase 1" would close the gap; silence next to an explicit PWA claim reads as an oversight, not a decision.
- **medium** No surface has a defined empty or cold-load state (e.g., Dashboard with zero orders yet today, Pacientes with no search results, Auditoría with no matching filter). Neither example file skips this category — both have explicit empty/cold-load rows. *Fix:* at minimum, note Dashboard and Pacientes empty states; the rest can be marked out of scope at spine granularity.
- **low** Permission-denied is handled, but only as one global rule in Accessibility Floor ("RBAC is visible, not silent," `EXPERIENCE.md` line 113) rather than per-surface. This is a defensible design choice (one rule, applied everywhere) rather than an omission, but it means a downstream reader checking "what does Doctores look like for a Recepcionista" won't find a per-surface answer, only the general principle. Related: reconciliation notes (`reconcile-prompt-maestro.md` item 4) flag that the source maestro names Químico/Recepcionista as having a *partial* Dashboard view, which `EXPERIENCE.md`'s Dashboard IA row and RBAC note don't address directly — worth a second look against the PRD's actual role/permission definitions, though this reviewer did not independently re-verify that specific role-split claim against the PRD.

## 5. Visual reference coverage — N/A-for-now

Confirmed: `mockups/`, `wireframes/`, and `imports/` do not exist under this workspace. `.working/` contains four `direction-*.html` files and a `source-digest.md` — pre-Finalize direction explorations, not rendered mockups. This is expected at this stage of the workflow (Finalize/mockup-rendering is a later step per the task's own framing) and is correctly not counted as a gap.

## 6. Bloat & overspecification — strong

No meaningful padding found. Literal hex/pixel values are restated alongside token names in prose (e.g. `DESIGN.md` line 154: "Navy (`{colors.navy}` `#0D1B36`)"), which matches the convention in all three DESIGN.md examples rather than being redundant duplication. Every prose paragraph in both files ties to a specific decision, an FR/NFR citation, or a resolved client open-question — spot-checked FR-29, FR-38, FR-43, FR-44, FR-46, FR-52, FR-79, NFR-6, NFR-9 against `prd.md` and all resolved to real, matching requirements. No source restatement (personas/FRs/scope) found dressed up as UX rationale — the Brand & Style and State Patterns prose consistently explains *why* a decision was made, not *what the PRD already said*.

## 7. Inheritance discipline — thin

`sources` frontmatter in `EXPERIENCE.md` (lines 4–6, pointing to `prd.md` and `addendum.md` under `prd-quimiaio-2026-07-05/`) resolves — both files exist and were spot-checked. Token references from `EXPERIENCE.md` prose back to `DESIGN.md` mostly resolve correctly (`{components.input-pill}`, `{components.kanban-card-aging}`). The one broken link is the `critical-alert` reference already flagged in Finding 3 above — repeating it here because it is specifically an inheritance-discipline failure (a named cross-file pointer that doesn't resolve), not just a coverage gap.

### Findings
- **low** Component naming drifts slightly across the two files: `DESIGN.md` names it "Branch-switcher chip" (`components.branch-switcher-chip`, line 126) while `EXPERIENCE.md`'s Component Patterns row is titled "Branch switcher" (line 70). Unambiguous in context, but not an identical string. *Fix:* align the two labels exactly (either "chip" everywhere or neither).

## 8. Shape fit — strong

`DESIGN.md` section order is an exact match to the canonical order (Brand & Style → Colors → Typography → Layout & Spacing → Elevation & Depth → Shapes → Components → Do's and Don'ts). `EXPERIENCE.md` has every required default section (Foundation, IA, Voice and Tone, Component Patterns, State Patterns, Interaction Primitives, Accessibility Floor, Key Flows) plus both triggered sections used correctly (Inspiration & Anti-patterns — the client named three anti-patterns directly during discovery; Responsive & Platform — the product spans phone/tablet/desktop with materially different primary surfaces per flow). Key Flows correctly appears last in both this file and both example files.

### Findings
- **low** The relative order of the two triggered sections is swapped versus the `experience-example-shadcn.md` reference (Quimia IO: Inspiration & Anti-patterns then Responsive & Platform; Drift example: Responsive & Platform then Inspiration & Anti-patterns). No explicit order-lock rule for these two sections was found in the reference material for EXPERIENCE.md (unlike DESIGN.md's explicit lock), so this is noted only as a minor consistency observation, not a violation.
